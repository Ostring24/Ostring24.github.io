今早试用了下GPTs，里面躺满了基于chatgpt打造的各种垂直类GPTs，官方商店已收录超 3 000 个 GPTs，但热度较 2024 年底峰值明显回落，OpenAI 在多次峰会中坦言“策略会大改”，并建议开发者“先围绕 ChatGPT 做，别重押 GPTs。

一句话：GPTs 作为“轻量级角色包”在 2024 短暂吸睛后，没能跨越“付费墙、僵尸供给、场景浅薄”三道坎，而 OpenAI 也顺势把重心转向更可控、更赚钱的 2B API 和即将上线的「Skills」模块，C 端热度自然滑落

用户回到传统应用，他们的痛点是什么：我们其实不擅长对话提问

当前普通用户使用大语言模型的通常场景是把它当作一个可见即可得的搜索引擎工具，更深度一点，是作为一个多轮对话的调研工具，我总结下来有几个应用方向：

1. coding ：plan edit 以及一系列review等pipeline都属于这一大类
2. 单点查询搜索：某个知识点或者单一问题解答
3. 富媒体文件解析：论文，投资研报等信息密度高的文档
4. 垂类规划：旅行，调研等方向类问答都属于这一类

恰巧，黄仁勋在 ces 2026 上提到，未来所有应用程序都不会是预编译的，而是生成式执行在gpu的，这个思考有点意思。黄仁勋的论断核心是：
- 传统编程范式：开发者编写代码、将其编译成二进制指令，随后在 CPU／GPU／其他硬件上执行。
- 未来计算范式：开发者更多依赖 大模型（LLM）或智能体 来“生成”应用执行结果——实时推理和生成内容，而非运行预先编译好的逻辑。

换句话说——应用逻辑本身由 AI 模型在运行时动态生成或修改，而不是运行静态代码，这种模式伴随 GPU 作为主要执行引擎和推理载体，而非传统意义的 CPU “载体”。

那当下的应用应该怎么设计去满足从用户的需求到infra 的变化？


# 设计模式

| 层级 | 执行方式 | 特点 |
|---|---|---|
| 底层执行核 | 传统编译代码（CPU / CUDA kernel） | 高确定性、低延迟 |
| 中间策略层 | Rule + Policy + ML | 可控、可回溯 |
| 高层认知层 | LLM / Agent（GPU 推理） | 非结构化、生成式 |

#### 传统 API（面向流程）

```http
POST /createOrder
POST /pay
POST /confirm
```

#### 面向未来的 API（面向意图）

```json
{
  "intent": "完成一次购买",
  "constraints": {
    "budget": 500,
    "deadline": "当天"
  }
}
```

> LLM / Agent 可以规划执行路径、动态选择工具、调度 GPU 推理。  
> 接口设计必须允许未来接入生成式执行。


### 把复杂逻辑视作生成式候选

- **经验法则**：if-else 超过 3 层、规则超过 20 条 → 潜在生成式候选。
- **实践**：
  - 抽象成 DSL / 策略表 / 可解释输入输出
  - 输入：用户画像 + 场景  
  - 输出：决策建议 + 解释


### 将 AI 作为“执行引擎”，而不是插件

```text
Application Runtime
├── CPU Tasks
├── GPU Inference Tasks
├── Memory / KV Cache
└── Tool Invocation
```

- 推理是常驻负载  
- 需要上下文生命周期管理  
- 支持并发与批处理  

### 为“不确定性”设计兜底机制

- **Fallback Path**  
- **Confidence / Score**  
- **人工或规则回退**  

```text
LLM 决策置信度 < 阈值 → 走规则引擎
```


## 适合和不适合生成式执行的应用领域

### 适合的领域

- 智能客服 / Copilot
- 推荐 / 导购 / 咨询
- 协议理解、文档理解（RAG QA）
- 复杂调度、策略建议
- 数据分析解释层（非计算核心）

### 不适合激进生成式的领域

- 实时控制（工业、汽车）
- 金融清算核心链路
- OS / 驱动 / 编译器底层
- 强合规、强可验证系统
